# preflight-check · 发布前检查

## 一、它检查什么（一句话）

**这一版能不能发出去、发出去的到底是不是这一版 —— 三件事一次说清：**
**① 密钥不会跟着代码泄漏；② 公网能打开、且线上就是本地这一份；③ 部署配置本身没矛盾。**

这句话是这个技能的边界：它只审「发布这件事」，不审功能对不对、不审页面好不好看、
不审数据库里数据脏不脏。功能对不对是各自的检查技能（比如 `filter-check`）的事。

**为什么要专门做这个技能**：前面二十几天，出过的岔子全是「本地说好了、线上不是」这一类 ——
密钥可能混进提交、`dist/` 打包漏了新的、公网还挂着三天前那份。
这些毛病**自己在编辑器里看永远看不出来**，只有拿工具去问「线上到底是哪一版」才会现形。

## 二、什么时候用它

- **要发之前**：三块一起跑一遍，A / C 必须全绿才发（B 见下面第 5 条）
- **发完之后**：再跑一遍，这次重点看 B 板块 —— 确认线上真的换成新版了
- 怀疑「本地改了但线上还是旧的」时
- 改过 `.gitignore` / `cloudbaserc.json` / 路由，或者往仓库里加过新文件之后

## 三、检查清单（逐条过）

### 板块 A · 密钥别泄漏（发之前必须全绿）

| 编号 | 检查什么 | 怎么算过 |
| --- | --- | --- |
| **A1** | **敏感文件没被 Git 跟踪** | `git ls-files` 里不出现 `.env`、`.env.*`、`*.key`、`*.pem`、`*.p12`、`*.pfx` |
| **A2** | **被跟踪的文件里没有硬编码密钥** | 所有被跟踪的文本文件里，**不出现 `.env` 中任何一个非空敏感值**（键名含 KEY/SECRET/TOKEN/PASSWORD 一类，值 ≥12 字）；也不出现 `"role":"service_role"`、`-----BEGIN … PRIVATE KEY-----`、疑似 JWT（`eyJ….eyJ….xxx`） |

> A2 是**整个技能里最重要的一条**。密钥泄漏一旦提交，Git 历史是永久的 —— 推上去就删不干净了。
> 它的做法不是「猜哪些文件可疑」，而是**把 `.env` 里的真值拿去跟每个跟踪文件比对** ——
> 只要那个值在任何要提交的文件里露过面，就报出来。假的是真不了的。
>
> ⚠️ **一条例外（2026-10-12 补，理由按下面「硬规矩 2」的要求写在这里）**：
> 三条「**特征字样**」比对（私钥头 / `service_role` 标记 / 疑似 JWT）**跳过技能自身目录**
> `skills/preflight-check/`。因为它是检查器——文档和脚本里**必然**写着这些要查的字样本身
> （`SKILL.md` 这段在说明它、`run-preflight.js` 里是让它去查它），让它参与比对就会**永远自我命中**，
> 那是一条**假的 FAIL**（Day 26 实测踩到：技能被提交后 A2 立刻红了两条，红的正是它自己）。
> 这不是放宽：**最要紧的「`.env` 真值比对」不跳过**，仍全量扫 —— 真把密钥值写进技能目录照样抓得到；
> 换成别的文件里出现这些字样，也照抓不误。只有「检查器自己的措辞」被豁免。

### 板块 B · 公网能打开且是最新

| 编号 | 检查什么 | 怎么算过 |
| --- | --- | --- |
| **B1** | **公网首页能打开** | `GET https://<环境>-<号>.tcloudbaseapp.com/` 返回 **200** |
| **B2** | **公网接口可达且是对的这份** | `GET …/api-health` 返回 200，且 `service=habit-board-api`、`envId` 与 `.env` 里的 `ENV_ID` 一致 |
| **B3** | **公网那份是最新** | 公网上的 `index.html / app.js / cloud.js / style.css / theme.css / dashboard.*` 与**本地源码**逐个比字节数，全相等才算过 |

> **B3 是「发之前跑会红、发之后跑应该绿」的那一条。** 它的意思是：
> 「本地已经比线上新了，该重新打包上传了。」**发之前看到它红是正常的**，不是脚本坏了 ——
> 它就是在提醒你「别拿着旧版当作已发布」。反过来，发完之后它要是还红，那才是真出事了。

### 板块 C · 发布配置自洽

| 编号 | 检查什么 | 怎么算过 |
| --- | --- | --- |
| **C1** | **`.gitignore` 挡住了该挡的** | 实测 `git check-ignore` 对 `.env` 和 `dist/` 都返回「被忽略」 |
| **C2** | **路由契约与部署配置对得上** | `api-contract.md` 里那张**路由表**声明的每条 `/api…`，都能在 `cloudbaserc.json` 的 `gateway.routes` 里找到；反过来也成立（比较时忽略 `/api/health` 与 `/api-health` 这种「斜杠 vs 连字符」的写法差异） |

## 四、怎么跑

技能自带可执行脚本 `run-preflight.js`，零依赖（只用 Node 内置模块，**不开浏览器**）。

```bash
# 在项目根目录下：
"C:\Users\LM\.workbuddy\binaries\node\versions\22.22.2\node.exe" skills\preflight-check\run-preflight.js
```

- **退出码 0 = 全过**，**1 = 有 FAIL**（具体哪条看打印），2 = 脚本自身出错
- 结果同时写一份 `last-run.json` 到脚本同目录，供留档
- 可选环境变量 `PREFLIGHT_GIT`：指定用哪份 git（默认 PATH 里的 `git`）

## 五、判定的三条硬规矩

1. **不许只看「退出码 0」就说过了。** 必须翻输出里 A/B/C 每一条后面的**实际数字**
   （比如 A2 要看到「扫了多少个文件、比了几个敏感值」；B3 要看到「哪几个文件对不上、差多少字节」）。
   —— 这是项目 AGENTS.md「追加 2」要求的：写进结论的事实，要能指出核验动作。
2. **不许为了让检查过而放宽检查。** 这几条是发布纪律的翻版，改它等于改纪律。
   要真想放宽（比如某类文件不该扫），得先在 `SKILL.md` 里写清楚理由，再改脚本。
3. **B3 红了别急着改脚本。** 它红的意思通常是「该重新发布」，先去做那件事，再回来复跑。

## 六、它抓过什么（真实战绩）

| 日期 | 抓到什么 | 怎么发现的 |
| --- | --- | --- |
| 2026-10-12 | **一个被人为塞进仓库的密钥**（把 `.env` 里 `PG_API_KEY` 的值写进了要提交的文件） | A2 直接报出「哪个文件 ← 含 .env 里 PG_API_KEY 的值」 |
| 2026-10-12 | **公网还挂着旧版**：`app.js` 本地 29596 字节 / 线上 23410 字节，`cloud.js` 线上完全没有 Day 24 新增的 `sendJson` | B3 逐个文件报出差了多少字节 |
| 2026-10-12 | **自己误报自己**：技能被提交（`d3514fc`）后，A2 开始命中 `SKILL.md` / `run-preflight.js` 里那两条规则字样（`"role":"service_role"`、私钥头写法）—— 因为 A2 只扫**被跟踪**的文件，技能**没提交时**它扫不到自己，一提交就撞上 | A2 报出「`skills/preflight-check/SKILL.md ← 含 …服务端密钥标记`」；已修：特征字样比对跳过技能自身目录，`.env` 真值比对不跳 |
