## 0. Bug 长什么样（用户视角，三步复现）

1. 打开页面（连得上云端时，右上角显示「**云端数据库**」）
2. 点「＋ 新建习惯」，名字随便填，保存 —— 页面上立刻出现这张卡片
3. **按 F5 刷新** —— 卡片不见了

## 2. ② 定位（排除掉其他原因，锁定真正原因）

「数据没了」这件事，可能的解释有一堆。逐个试，逐个划掉：

| # | 嫌疑 | 怎么试的 | 结论 |
| --- | --- | --- | --- |
| 1 | **网断了？** | 页面加载时的两个读请求 `GET /api/habits`、`GET /api/todos` → **都是 200** | ❌ 排除 |
| 2 | **库里数据坏了？** | `GET /api/habits` 返回 **count=6**，和页面上显示的 6 条对得上 | ❌ 排除 |
| 3 | **页面没渲染出来？** | 加完之后页面上确实有它（`页面上有这条: true`） | ❌ 排除 |
| 4 | **浏览器缓存骗人？** | 刷新时确实重新发了请求（Network 里能看到新记录） | ❌ 排除 |
| 5 | 云端把本机覆盖了？ | **是真的** —— 但这是「结果」不是「原因」：得先有「本机存了、云端不知道」的落差才成立 | ⚠️ 只对一半 |
| 6 | **页面压根没把改动送出去** | Network 里写请求 **0 条** | ✅ **真因** |

### 再往下一层：是「前端没接」还是「服务端没有」？

这一步不靠猜 —— **直接在页面里发那几个写请求，看服务端怎么答**。
原始实录：`day24-evidence/02-locate.txt`。

**这就是 F12 控制台里的报错原文（逐字）：**

```
POST https://habit-board-d0gum6nqu512acc29-1499798330.ap-shanghai.app.tcloudbase.com/api/todos
→ HTTP 405 Method Not Allowed
{"ok":false,"service":"habit-board-api","function":"api-todos","version":"v1.1",
 "error":"method_not_allowed","message":"这个接口只接受 GET"}

PATCH https://.../api/habits/h_seed_water     body: {"doneDates":[...当前值...]}
→ HTTP 400 Bad Request
{"ok":false,...,"error":"bad_request",
 "message":"没有要改的字段：请至少带上 name / freqType / freqCount 里的一个（id 和 createdAt 不能改）"}

PATCH https://.../api/habits/h_seed_water     body: {"name":"每天喝 8 杯水"}   ← 对照组
→ HTTP 200 OK  {"ok":true, ...}
```

Console 里对应的两行红字（**这就是要交的那张「报错原文」**）：

```
[error] Failed to load resource: the server responded with a status of 405 (Method Not Allowed)
[error] Failed to load resource: the server responded with a status of 400 (Bad Request)
```

> 对照组那条 `200` 很关键：它证明**服务端的写接口本身是好的**，不是坏在那儿。

### 定位结论（一张表说清）

| 页面动作 | 服务端有没有这个口 | 前端接了吗 |
| --- | --- | --- |
| 读习惯 / 读待办 | ✅ 有 | ✅ 接了（Day 17） |
| **新建习惯** `POST /api/habits` | ✅ 有（Day 18） | ❌ **没接** |
| **改习惯** `PATCH /api/habits/<id>` | ✅ 有（Day 22） | ❌ **没接** |
| **删习惯** `DELETE /api/habits/<id>` | ✅ 有（Day 22） | ❌ **没接** |
| **勾选完成**（要写 `doneDates`） | ❌ **不收**（PATCH 白名单里没有它） | ❌ 没接 |
| **待办的新增 / 改 / 删** | ❌ **只接受 GET** | ❌ 没接 |

**真因**：**服务端的写口从 Day 18 / Day 22 就备好了，前端一个都没接。**
页面上的改动只写了浏览器本机（localStorage），而页面一打开，`cloud.js` 的 `sync` 又会拿云端那份把本机覆盖掉 —— 改动就这么消失了。

> 这和 Day 21 验收表里那条 **W3-11 FAIL** 是同一件事（备注写着「已排第 4 周」—— 今天正是第 4 周）。

## 3. ③ 修复（改了什么、为什么）

**范围**：只修**服务端已经备好口**的那三个动作 —— **新建 / 改（名称、频率）/ 删习惯**。
另外两个（勾选完成、待办的增删改）**服务端还没有对应的口，不去硬凑**，记进第 5 节的「不做清单」。

| 文件 | 改了什么 |
| --- | --- |
| `cloud.js` | 新增 `sendJson(method, url, body)` —— 带超时的 `POST / PATCH / DELETE`，返回值统一成 `{ok, status, data, message, netError}`；对外新增 `createHabit()` / `updateHabit(id, patch)` / `removeHabit(id)`。**接口地址仍然只出现在这一个文件里**（契约 §6 那条规矩） |
| `app.js` | 新增 `cloudReady()` / `markUnsynced()` / `afterPush()` / `replaceHabit()`；`saveHabitForm()`（新建、编辑）和 `runDelete()`（删习惯）后面补上「推回库」这一步 |

**三条设计取舍（为什么这么写）：**

1. **本机为先，云端随后。**
   改完仍然是**先写 localStorage、先重画页面**（秒开、断网也能用），**再**异步把这次改动推回库。
   没有改成「等接口回了才更新页面」—— 那样网一慢，点一下要转半天圈。

2. **不许假成功。**
   推不上去**必须说出来**：把右上角那个小标改成「**没同步上云端**」+ 控制台留一行 `[写回库失败] …`，失败原因直接用服务端给的那句人话（Day 23 统一过口径）。
   绝不能出现「页面看着存好了、其实库里没有」—— 那正是契约 §4.4 一直在防的事。

3. **新建之后，用服务端那条替换本机那条。**
   契约 §3.8 推荐 `POST` **不传 `id`**（免得两个客户端撞上同一个 id），所以 id 由服务端生成；
   拿到返回的 `data` 之后把本机那条整体换掉，**以后的改 / 删才对得上号**。
